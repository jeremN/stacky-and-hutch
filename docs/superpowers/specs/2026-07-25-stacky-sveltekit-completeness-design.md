# sveltekit-completeness — make the SvelteKit brick produce a buildable app

**Goal:** Give the `sveltekit` web brick the SvelteKit project files it is missing so a generated `{ vite, sveltekit }` app actually builds (`pnpm build`) and type-checks (`pnpm typecheck`). This is the exact mirror of the `tanstack-completeness` fix — the SvelteKit side has the same class of gap, just discovered later.

## Why this slice, now

The S5 (TanStack Query) spike scaffolded a real SvelteKit app and found `pnpm build` fails immediately: `Error: src/app.html does not exist`. The `sveltekit` brick ships `hooks.server.ts`, `+layout.svelte`, `+page.svelte`, and `tsconfig.json`, but **not** the two files SvelteKit treats as non-optional (`svelte.config.js`, `src/app.html`) nor a deploy adapter. S3's "svelte clean" smoke only ran a Vitest component test (jsdom, via the Vite pipeline) — it never ran `svelte-kit build`, so the gap was invisible.

Two consequences of the missing `svelte.config.js` specifically:
- `svelte-kit build` / `svelte-kit dev` cannot run (no config, no `app.html` template).
- `svelte-kit sync` cannot run — and the `typecheck` brick's Svelte script is `svelte-kit sync && svelte-check`, whose `tsconfig.json` already `extends "./.svelte-kit/tsconfig.json"` (generated by `sync`). So typecheck is also blocked until `svelte.config.js` exists.

## Scope (YAGNI)

- **Buildability + typecheck only.** Add the three standard SvelteKit project files and one adapter dependency. No new features, no routes, no hooks changes (`hooks.server.ts` already exists and keeps its `server-init` seam untouched).
- **`@sveltejs/adapter-auto`, not a platform adapter.** stacky's container runs `npm run dev` (the `vite` brick's `Dockerfile` `CMD` is `npm run dev … --host 0.0.0.0`), so the adapter is only needed to make `pnpm build` *succeed*, not to produce a runnable server for the container. `@sveltejs/adapter-auto` is the `sv create` default, builds cleanly on any platform (warning-only on unknown hosts), and defers the platform-specific adapter choice to the user — the minimal, idiomatic choice. A specific adapter (node/vercel/…) is a later deploy concern, not this gap.
- **No `static/` / favicon.** `app.html` omits a favicon `<link>` so the brick ships no binary asset; SvelteKit builds fine without one.

## The three files (owned, byte-identical — no goldens)

### `svelte.config.js`

```js
import adapter from '@sveltejs/adapter-auto'
import { vitePreprocess } from '@sveltejs/vite-plugin-svelte'

/** @type {import('@sveltejs/kit').Config} */
const config = {
  preprocess: vitePreprocess(),
  kit: {
    adapter: adapter(),
  },
}

export default config
```

`vitePreprocess` comes from `@sveltejs/vite-plugin-svelte`, already a devDependency of the brick (`^5.0.0`). The vite integration itself (`sveltekit()` plugin) is already injected via the brick's `fragments/plugin.ts`.

### `src/app.html`

```html
<!doctype html>
<html lang="en">
  <head>
    <meta charset="utf-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1" />
    %sveltekit.head%
  </head>
  <body data-sveltekit-preload-data="hover">
    <div style="display: contents">%sveltekit.body%</div>
  </body>
</html>
```

`%sveltekit.head%` and `%sveltekit.body%` are the required template placeholders; `%sveltekit.body%` sits inside a `<div>` (not directly in `<body>`) per SvelteKit's guidance (it warns otherwise).

### `src/app.d.ts`

```ts
// See https://svelte.dev/docs/kit/types#app.d.ts for information about these interfaces
declare global {
  namespace App {
    // interface Error {}
    // interface Locals {}
    // interface PageData {}
    // interface PageState {}
    // interface Platform {}
  }
}

export {}
```

Optional for build, but it's what `sv create` scaffolds and where users add `Locals`/`PageData` types — included so the generated app matches an idiomatic SvelteKit project (parity with the now-complete tanstack side).

## Dependency

The brick's `fragments/package.json` gains `@sveltejs/adapter-auto ^7.0.0` (devDependency; peer `@sveltejs/kit ^2.0.0`, which the brick already provides).

## Prettier conformance

The generated app may include the `prettier` brick, whose `format:check` would inspect these owned files. During the runtime smoke, run `pnpm format` (or `prettier --check`) on the scaffold; if it rewrites any of the three files, update the brick source to the prettier-formatted bytes so a `{ …, prettier }` stack passes `format:check` out of the box. (The files are authored close to prettier defaults, so drift should be minimal or none.)
